# Контекст обсуждения фотооценки квартир — Алматы

Обновлено: 2026-10-02. Это конспект обсуждения для продолжения работы, а не
утверждённое ТЗ на все перечисленные изменения. Ниже разделены существующий код,
намерения пользователя, предложения и нерешённые вопросы. Секреты сюда не включать.

## Проект в целом

Перед изменениями читать `CLAUDE.md` и фактическую последовательность
`collector_job()` → `process_and_notify()` в `orchestrator_v7.py`.

Это один из трёх сервисов Алматы:

- Collector собирает карточки и отдаёт события `new` / `price_drop`.
- Almaty Cleaner выполняет очистку и строит baseline.
- Этот репозиторий получает события и baseline, оценивает привлекательность
  объявлений относительно baseline и отправляет результаты в Telegram.

Этот сервис не скрейпит сайт и не строит baseline. Baseline скачивается целиком
из Cleaner примерно каждые 12 часов и атомарно заменяет локальный файл.
Астанинская инстанция отдельная; общего состояния с ней нет.

Развёртывание — Render Background Worker, persistent disk `/var/data`.
Все постоянные данные должны жить под `KRISHA_DATA_DIR` / `DATA_DIR`.
Каталог `cache/` по проектному договору является временным: постоянный кэш
оценок нельзя размещать там. Текущий standalone-путь БД:
`DATA_DIR/interior/renovation.sqlite3`.

## Что пользователь хочет

Промт уже выбран. Первый этап — грамотно внедрить фотооценку отдельным модулем;
влияние на конечное решение о квартире разработать следующим этапом.
Обязательного семидневного shadow mode пользователь не хочет: проект пока
тестируется, искусственный период ожидания не нужен.

Нужен кэш, чтобы изменение только цены не вызывало повторную оплату оценки.
В перспективе объявления baseline и входящие объявления должны иметь оценку
по одинаковой методике. Недостаток фотографий не равен плохому ремонту:
для части объявлений корректный результат — отсутствие числового балла.

Пользователь просил убрать ненужные файлы и спрашивал, почему оставлены `_tmp_*`
и прежние пользовательские изменения. Это не основание автоматически удалять
все непонятные файлы. Предыдущий контекстный файл был ошибочно удалён при уборке;
этот файл восстановлен как конспект доступного обсуждения. Сохранять его.

## Существующая реализация

Подробности — `RENOVATION_SCORER.md` и исходники:

- `renovation_scorer.py`: промт, схема ответа, вызов модели, валидация.
- `renovation_store.py`: SQLite, результаты, связь ID с результатом, попытки.
- `renovation_worker.py`: скачивание фотографий, SHA-256, поиск кэша, оценка.
- `run_renovation_standalone.py`: отдельный прогон реальной карточки.
- `test_renovation_scorer.py`, `test_renovation_worker.py`: проверки без API.

На момент обсуждения фотооценка ещё не подключена к оркестратору. В рабочем
дереве есть другие изменения оркестратора и проекта; не считать их частью
фотоинтеграции и не перезаписывать.

Зафиксированная конфигурация оценщика:

- `gpt-6-luna`, версия `simple-decimal-v1-gpt6-luna`;
- Responses API, Structured Outputs;
- `temperature=0`, `reasoning.effort=none`, изображения `detail=low`;
- до 1400 выходных токенов;
- один запрос по подготовленному набору фотографий;
- общий визуальный балл интерьера 1.0–10.0 с шагом 0.1.

Результат: `score`, `coverage`, `evidence`, `limitations`.
`coverage`: `sufficient`, `partial`, `insufficient`.
При `insufficient`: `score=null`, `evidence=[]`, причина в `limitations`.
Отдельного поля `confidence` и отдельных компонентных баллов в согласованной
схеме нет. Не добавлять их как будто они уже согласованы.

Это оценка визуального качества интерьера, а не смета стоимости ремонтных работ.

Кэш уже реализован:

```text
content_set_key = SHA256(отсортированного уникального набора SHA256 байтов фото)
evaluation_key = ключ от content_set_key и версии оценщика
listing_id → evaluation_key
```

Цена, описание, причина события и ID не входят в ключ самого результата.
Перестановка и точные дубли фото не меняют его. Одинаковые наборы байтов под
разными ID могут использовать одну оценку. Изменение фото или версии оценщика
создаёт другой ключ. Модель, промт, схема и правила валидации требуют обновления
версии при изменении.

Worker пока скачивает фото даже для проверки попадания в кэш. Это экономит
вызовы модели, но не повторное скачивание. Постоянно байты фото не сохраняются;
в payload сохраняются результат, метаданные и manifest с URL/хешами.
В БД уже есть таблицы `results`, `listing_results`, `attempts`.

`no_photos` сейчас возвращается из worker без API-вызова, но не записывается
как постоянный результат. Полноценной постоянной очереди и состояний
`pending/error/no_photos` по каждому ID пока нет. Не путать состояние задания
с достаточностью фотографий (`coverage`).

## Предложение пользователя: первичный baseline и дальнейший обмен

Пользователь предложил:

1. Вначале заморозить данные и, возможно, выполнить первичную фотооценку в
   Almaty Cleaner.
2. Получить baseline с оценками ремонта.
3. Затем отключить фотооценку в Cleaner, оставив её только в этом сервисе.
4. Здесь хранить минимум данных (пользователь привёл JSON с ID/хешем как пример),
   чтобы не раздувать хранение/память.
5. Cleaner обращается сюда и получает оценки по ID для последующих baseline.

Ключевая идея: после начального заполнения один владелец вычисления фотооценок.
Отключение фотооценки Cleaner не означает отключение его текстовой AI-очистки.
Не реализовывать заново начальный прогон, если совместимые оценки уже существуют:
нужен перенос кэша вместе с ID, отпечатком фото и версией оценщика.

## Уточнённое предложение ассистента — пока не утверждено

В первом ответе ассистент предложил лишний отдельный API-сервис и общий диск/
Postgres, а также несуществующие поля оценки. После замечания пользователя
перечитал `CLAUDE.md` и код и исправил рекомендацию.

Более простой вариант для рассмотрения: этот worker отправляет новые готовые
оценки в существующий HTTP-сервис Cleaner. Cleaner сохраняет компактную копию
и присоединяет её к baseline. Так не требуется входящий HTTP в оркестраторе.
Новый принимающий endpoint в Cleaner ещё нужно реализовать; наличие такого
endpoint сейчас не подтверждено, код другого репозитория не исследован.

Это изменение направления запроса относительно идеи пользователя, а не уже
принятое решение. Пользователь пока попросил только сохранить контекст.

Если выбрать отправку результатов, нужна постоянная отметка непереданных
записей и повторная доставка без повторной фотооценки. Повторная отправка одного
результата должна быть безопасной. Cleaner должен уметь строить baseline по
имеющимся данным при временной недоступности обмена.

SQLite здесь уже есть и подходит для компактных результатов: файл на диске
не требует загрузки всей базы в RAM. Текущий worker, напротив, держит скачанные
изображения и base64 в памяти. Перед массовым прогоном нужно ограничить пик
памяти/параллелизм; лимит 200 MiB проверяется после скачивания набора и не
является надёжным ограничением пикового RAM.

## Открытые вопросы интеграции

- Где выполнить первичное заполнение: Cleaner или standalone здесь? Заморозить
  конкретный снимок и версию оценщика; способ остановки/возобновления обновлений
  и точный состав заморозки пока не согласованы.
- Как обмениваться результатами: Cleaner запрашивает здесь (идея пользователя)
  или worker отправляет в Cleaner (последнее предложение ассистента)?
- Как сопоставлять версию фото между сервисами? Один ID недостаточен. Сейчас
  хеш здесь считается по байтам, и Cleaner не проверит его только по URL.
  Нужен согласованный идентификатор/отпечаток набора; хеш URL не эквивалентен
  хешу содержимого.
- Как покрыть объявления, пропущенные лентой? Здесь обрабатываются `new` /
  `price_drop`, старые события отсекаются, первый запуск может начинаться с
  конца ленты. Обновление только фото не гарантированно создаёт нужное событие.
  Предложена сверка обновлённого baseline с кэшем и дооценка пропусков здесь.
- Как сделать фотообработку независимой от Stage 2? Постановка задания после
  получения карточки до Stage 2 возможна, но простого переноса вызова мало:
  сейчас весь `collector_job()` ждёт baseline, а повтор страницы связан со
  Stage 2. Нужны определённые правила очереди, повторов и продвижения курсора.
- Как передавать отсутствующие/устаревшие оценки, хранить no_photos, ограничить
  рост журнала попыток и версий, обеспечить возобновляемость массового прогона?

## Влияние ремонта на конечное решение

Финальная формула не согласована и не реализована.

В раннем обсуждении рассматривалась шкала состояния C1–C6 и ограниченная
поправка к ценовому отклонению, способная менять verdict. По восстановленному
контексту этот подход затем отвергли как необоснованный, если известно состояние
только оцениваемой квартиры, но неизвестно состояние аналогов.

Упоминалась формула `B_adjusted = B_raw * (1 + a)` и
`diff_adjusted = 1 - price_m2 / B_adjusted`, где `a` должен быть получен из данных.
Это исторический вариант, не выбранная формула и не разрешение внедрить
произвольные проценты премии за ремонт.

Обогащение baseline одинаковыми фотооценками даст данные для сравнения ремонта
кандидата с аналогами. Затем нужно отдельно выбрать и проверить способ влияния
на цену/итоговый verdict. При сужении когорт помнить: меньше аналогов → ниже
benchmark_confidence → выше порог НАХОДКА. Фотооценку нельзя автоматически
приравнивать к существующему `quality_evidence_score`.

## Аудит 2026-10-02

После первого массового теста проведён отдельный аудит рисков. Полный список:
`RENOVATION_SCORER_AUDIT.md`. Перед граничным прогоном исправлены порядок фото и
исключение общих зон/рендеров из score; версия оценщика поднята до
`simple-decimal-v2-gpt6-luna`. Остальные пункты аудита не считать исправленными.

После этого продолжена техническая доработка: частичный CDN-сбой больше не
отменяет доступные фото; одинаковый `price_drop` использует URL fast-path без
скачивания; параллельные одинаковые evaluation key внутри одного процесса
делают один API-вызов; состояния сохраняются в SQLite. Для фотооценки предусмотрен
отдельный `RENOVATION_OPENAI_API_KEY` с fallback на основной ключ.

Оригинальные фото постоянно не хранятся. JPEG preprocessing v3 был проверен,
но затем отклонён: A/B показал различия до 0.2 балла и один скачок coverage,
тогда как реальные наборы по 100 URL занимали лишь 5.56/8.50 MiB. Финальная
версия `simple-decimal-v4-original-gpt6-luna` отправляет оригиналы с `detail=low`,
скачивает их пачками по два и ограничивает один набор 15 MiB. Pillow удалён.

Исторический v3-прогон оставлен только как эксперимент. Его полезный результат:
URL fast-path на повторе сделал 0 скачиваний и 0 API-вызовов. Первые 30 кадров
`1015797426` дали `insufficient` и `score=null`; после отказа от v3 этот сценарий
был назначен на повторную проверку финальной v4.

Финальная v4 перепроверка выполнена. Две полные карточки со 100 URL получили
4.6/sufficient и 6.2/sufficient; набор из первых 30 кадров `1015797426` только
с ЖК/холлом получил `insufficient`, `score=null`, пустой evidence. Повтор полных
карточек сделал 0 скачиваний и 0 API-вызовов. Store дополнен единым экспортом
компактных `interior_*` полей для присоединения к baseline.

Граничный прогон v2 сохранён в
`interior/sample_20261001T200234Z.json`: 12 карточек, 10 API-вызовов, один
`no_photos`, один полный сбой из-за CDN 404, остальные успешно. Карточки с
1–4 фото получили `partial`; контрольные и большие — `sufficient`. Модель
корректно исключила общие зоны в известных сложных карточках. Полные выводы и
оставшиеся пробелы добавлены в аудит.

## ОКОНЧАТЕЛЬНЫЙ контракт online-интеграции (приоритет над прежними идеями)

Зафиксировано пользователем после уточнения архитектуры. Этот раздел отменяет
любые прежние предложения о полном списке фото-кандидатов, новом endpoint
Collector, полной сверке его baseline или отдельной фото-ленте.

1. Mainrieltor использует уже существующий поток Collector: получает новые и
   изменённые ID из текущей ленты, затем получает полную карточку через уже
   существующий механизм. Никакого нового полного списка кандидатов и никакого
   нового endpoint Collector для фотооценки не создаётся.
2. Каждая карточка, которую Mainrieltor уже забрал у Collector, проходит шлюз
   фотооценки. Это не означает обязательный вызов модели: сначала проверяется
   актуальность сохранённого результата.
3. Межсервисный ключ актуальности:
   `listing_id + photo_set_hash + evaluator_version`. `photo_set_hash` приходит
   в карточке Collector. Изменение только цены не требует новой фотооценки.
4. Mainrieltor ищет совпавший ключ в двух местах: (а) в последнем clean baseline,
   скачанном у Cleaner; (б) во временной таблице новых результатов Mainrieltor.
5. Если ключ найден, используется готовая оценка и OpenAI не вызывается. Если
   ключ не найден (новый ID, новые фотографии или новая версия оценщика),
   Mainrieltor выполняет оценку и сразу сохраняет результат во временную таблицу.
6. Cleaner в online-потоке не выдаёт задания и не является источником карточек.
   Его роли только две: отдавать Mainrieltor clean baseline с опубликованными
   оценками и забирать у Mainrieltor временные новые результаты.
7. Cleaner после успешной публикации нового baseline подтверждает конкретные
   результаты. Mainrieltor удаляет только подтверждённые записи спустя 24 часа;
   неподтверждённые по возрасту не удаляются.
8. Полной постоянной копии всех фотооценок в Mainrieltor нет. Первоначальные и
   уже опубликованные оценки живут в baseline Cleaner; Mainrieltor хранит только
   временные новые результаты до подтверждения.
9. Mainrieltor в итоге станет Web Service, чтобы Cleaner мог забрать результаты
   и подтвердить их. Сначала всё реализуется и проверяется локально.

Нельзя без нового прямого решения пользователя добавлять полный обход
`/baseline/table` Collector, `/listings/photo-candidates`, отдельную фото-ленту,

## Реализованный online-слой Mainrieltor (2026-10-02)

Источник карточек не меняется: используется только существующая лента Collector
`/listings/changes` и уже выполняемый запрос `/listings/{id}`. Отдельной полной
выгрузки кандидатов, сверки Collector или второй ленты нет.

Каждая полученная карточка при включённом `INTERIOR_ENABLED` проходит шлюз до
Stage 2:

1. Проверяется точный `photo_set_hash` Collector на исходном списке URL.
2. Ищется точное совпадение `listing_id + photo_set_hash + evaluator_version`
   сначала в последнем baseline Cleaner, затем во временной таблице Mainrieltor.
3. Совпадение переиспользуется; изменение одной цены новый API-вызов не создаёт.
4. Новый ключ сохраняется в SQLite-очередь. Результат каждой квартиры пишется
   сразу. `no_photos` становится terminal без вызова модели.
5. Worker использует исходный `simple-decimal-v4-original-gpt6-luna`,
   `max_retries=0`, timeout 180 секунд и до трёх управляемых попыток за запуск.
   401/403 останавливает выдачу новых задач фотооценки.

Cleaner забирает только terminal-результаты через
`GET /interior/evaluations?limit=N`, публикует baseline и подтверждает конкретные
`evaluation_id` через `POST /interior/evaluations/ack`. Выдача намеренно не
использует watermark `after_id`: при нескольких workers более старый ID может
завершиться позже и иначе навсегда оказаться позади курсора. Безопасный цикл:
получить первые unacked → успешно опубликовать → ACK → получить следующую пачку.
ACK pending/error запрещён и идемпотентен.

Подтверждённый результат удаляется спустя 24 часа. Неподтверждённый по возрасту
не удаляется. Одновременно удаляется только осиротевший content-cache; кэш,
который ещё нужен другой временной записи, сохраняется.

Локальный живой прогон: карточка Collector содержала 14 фото, её hash совпал с
контрактом; оценка завершилась `ready` за один API-вызов; повтор с другой ценой
переиспользовал тот же `evaluation_id`. Строка оставлена unacked до настоящей
публикации Cleaner.

## Реализованное влияние на итоговую оценку (2026-10-03)

- Сравнивается ремонт цели с ремонтом тех же ценовых когорт.
- Формула асимметрична: `base * exp(beta * score_delta * confidence)`, где
  `beta=0.12` для ремонта хуже аналогов и `0.04` для ремонта лучше аналогов;
  ограничение по модулю 0.15 в log-шкале. Неизвестная оценка даёт нулевую
  поправку.
- На свежем baseline из 10 262 строк числовая оценка есть у 9 556 (93.1%).
  На hold-out из 2 037 строк средняя относительная ошибка снизилась
  `0.1545 -> 0.1402`, медианная `0.1040 -> 0.0992`.
- Свежая карточка durable сохраняется в SQLite и ждёт фотооценку до 20 минут;
  Collector при этом продолжает двигать курсор. После рестарта очередь
  продолжается. Свежие карточки приоритетнее исторического backfill.
- После timeout Stage 3 работает без поправки: сбой фотооценки не блокирует
  основной сервис и неизвестное состояние не превращается в фиктивный ноль.
- Telegram и `notifications_log_v4.csv` показывают ремонт аналогов и процент
  поправки справедливой цены.
