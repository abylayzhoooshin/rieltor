# rieltor-orchestrator

Мониторинг аренды квартир в Астане на krisha.kz: сервис забирает новые и
подешевевшие объявления, оценивает каждое против эталонной базы честных
цен и присылает в Telegram только то, что стоит внимания — находки и
подозрительные объявления.

## Как это устроено

Это один из трёх сервисов. Сам он **не ходит на krisha.kz** и **не
собирает baseline** — только потребляет два соседних сервиса:

```
rieltorcollector ──(лента событий new/price_drop)──┐
                                                   ├──> rieltor-orchestrator ──> Telegram
rieltor-cleaner  ──(готовый baseline, раз в 12ч)───┘        (этот репозиторий)
```

Цикл одного объявления:

```
GET /listings/changes  — курсорная лента событий (new / price_drop)
GET /listings/{id}     — полная карточка по каждому событию
  → pipeline/incoming_clean_v2.py   мягкая очистка (ничего не выбрасывает)
  → pipeline/stage2_llm_analyze.py  разбор описания через OpenAI
  → pipeline/stage3_benchmark_v3.py оценка против baseline, вердикт
  → дедуп по ever_sent_ids.json     шлём, только если цена строго упала
  → запись в журнал, потом Telegram (outbox-first)
```

**Вердикты Stage 3:** НАХОДКА, СПРАВЕДЛИВАЯ, ПЕРЕОЦЕНЕНА, ТРЕБУЕТ
ПРОВЕРКИ, РУЧНАЯ ПРОВЕРКА, НЕДОСТАТОЧНО ДАННЫХ. В Telegram уходят
НАХОДКА и ТРЕБУЕТ ПРОВЕРКИ всегда, РУЧНАЯ ПРОВЕРКА — только если
объявление вдобавок заметно дешевле базы.

**Дедуп** — главное правило всего слоя: объявление уходит повторно,
только если его цена **строго ниже** цены на момент прошлой отправки.
Это само по себе гасит «подъёмы» объявления в топ без изменения цены.

**Outbox-first:** запись в журнал и реестр происходит *до* отправки в
Telegram. Неудачная отправка не приведёт к повторной рассылке на
следующем цикле, зато останется в `notifications_log_v3.csv`.

## Структура

| Путь | Что это |
|---|---|
| `orchestrator_v7.py` | точка входа: опрос ленты, дедуп, доставка |
| `pipeline/stage3_benchmark_v3.py` | вся логика оценки и вердиктов |
| `pipeline/stage2_llm_analyze.py` | разбор описаний через OpenAI |
| `pipeline/incoming_clean_v2.py` | мягкая очистка входящих строк |
| `tools/eval_stage3.py` | замер качества оценки: старая версия против новой |
| `backup_pre_area/` | прошлая версия Stage 3 — эталон для сравнения в `tools/eval_stage3.py` |
| `for_ms3/` | спецификация API соседнего сервиса-сборщика |

## Локальный запуск

Нужен Python 3.12 (работает и на 3.10).

```bash
pip install -r requirements.txt
cp .env.example .env      # и вписать реальные ключи
python orchestrator_v7.py
```

Остановить — Ctrl+C: текущая страница событий доработает до конца.

Замер качества оценки на hold-out выборке:

```bash
python tools/eval_stage3.py --targets 2500 --seeds 1
```

## Деплой на Render

Сервис — **Background Worker**, не Web Service: он не слушает HTTP, а
бесконечно опрашивает ленту раз в 60 секунд. Free-тариф Render усыпляет
web-сервисы через 15 минут без запросов и не даёт постоянный диск.

1. Залить репозиторий на GitHub.
2. Render Dashboard → **New → Blueprint**, выбрать этот репозиторий.
   Render прочитает `render.yaml` и заведёт сервис сам.
3. Render спросит значения секретов (те, что помечены `sync: false`).
   Вписать:

   | Переменная | Обязательна | Что это |
   |---|---|---|
   | `RIELTOR_COLLECTOR_URL` | да | адрес сервиса-сборщика, без пути |
   | `RIELTOR_COLLECTOR_API_KEY` | да | его ключ (заголовок `X-API-Key`) |
   | `RIELTOR_CLEANER_API_KEY` | да | ключ сервиса baseline (см. ниже) |
   | `OPENAI_API_KEY` | да | без него Stage 2 не работает и сервис не стартует |
   | `TELEGRAM_BOT_TOKEN` | нет | без него работает молча, только журнал |
   | `TELEGRAM_CHAT_ID` | нет | узнать через `getUpdates` своего бота |

4. Проверить в логах строку `DATA_DIR = /var/data (состояние,
   ПЕРСИСТЕНТНЫЙ)` — значит диск подключился.

### Почему ключ `RIELTOR_CLEANER_API_KEY` обязателен

Файл baseline (28 МБ) намеренно **не лежит в репозитории**: он
пересобирается сервисом `rieltor-cleaner` раз в 12 часов, и держать его
в git значило бы добавлять в историю 28 МБ при каждом обновлении.
Оркестратор скачивает его сам при старте. Пока файла нет, опрос ленты
пропускает такты и пишет в лог `baseline ещё не загружен` — это
нормально первые пару минут после первого деплоя.

### Постоянный диск

`render.yaml` монтирует диск в `/var/data` и задаёт
`KRISHA_DATA_DIR=/var/data`. Туда попадает всё изменяемое состояние:

- `ever_sent_ids.json` — реестр отправленного;
- `collector_state.json` — курсор ленты событий;
- `notifications_log_v3.csv` — журнал отправок;
- `baseline/` — скачанный эталон;
- `cache/` — промежуточные файлы прогона.

Код при этом читается из слепка репозитория. Разделение важное: без
диска реестр отправленного обнулялся бы при каждом деплое, и бот заново
рассылал бы то, что уже отправлял.

Локально `KRISHA_DATA_DIR` задавать не нужно — состояние ляжет рядом со
скриптом, как и раньше.

### Ресурсы

Тариф Starter (512 МБ) с запасом: baseline занимает в памяти ~90 МБ,
пик при загрузке ~101 МБ (замерено на 13 390 строках), загрузка ~0.4 с.
Регион в `render.yaml` — `frankfurt`; его стоит поменять на тот, где уже
работают соседние два сервиса, иначе каждый запрос к ним идёт лишние
тысячи километров.

## Безопасность

Токен Telegram-бота раньше был зашит в `orchestrator_v7.py` и попал в
историю git. Сейчас в коде его нет — только переменные окружения, — но

токен стоит считать скомпрометированным и перевыпустить у
[@BotFather](https://t.me/BotFather) (`/revoke`).
